#初探反调试
2024-10-17

探测Windows调试器

  • 使用Windows API

IsDebuggerPresent查询进程环境块中的isdebugged标志。如果进程没有运行在调试器环境中，函数返回0；如果调试附加了进程，函数返回一个非零值。

BOOL CheckDebug()  
{  
    return IsDebuggerPresent();  
}

CheckRemoteDebuggerPresent同IsDebuggerPresent几乎一致。它不仅可以探测进程自身是否被调试，同时可以探测系统其他进程是否被调试。原理是将一个进程句柄作为参数，检查这个句柄对应的进行是否被调试器附加。如果函数成功，则返回值为非零。

BOOL CheckDebug()  
{  
    BOOL ret;  
    CheckRemoteDebuggerPresent(GetCurrentProcess(), &ret);  
    return ret;  
}

NtQueryInformoationProcess属于Ntdll.dll文件中的一个API

//以调试端口为例，如果成功，返回进程端口，失败则返回0
BOOL CheckDebug()  

{  

    int debugPort = 0;  

    HMODULE hModule = LoadLibrary("Ntdll.dll");  

    NtQueryInformationProcessPtr NtQueryInformationProcess = (NtQueryInformationProcessPtr)GetProcAddress(hModule, "NtQueryInformationProcess");  

    NtQueryInformationProcess(GetCurrentProcess(), 0x7, &debugPort, sizeof(debugPort), NULL);

}

OutputDebugString和GetLastError：使用SetLastError函数，将当前的错误码设置为一个任意值。如果进程没有被调试器附加，调用OutputDebugString函数会失败，错误码会重新设置，因此GetLastError获取的错误码应该不是我们设置的任意值。但如果进程被调试器附加，调用OutputDebugString函数会成功，这时GetLastError获取的错误码应该没改变。

BOOL CheckDebug()  
{  

    DWORD errorValue = 12345;  
    SetLastError(errorValue);  
    OutputDebugString("Test for debugger!");  
    if (GetLastError() == errorValue)  
    {  
        return TRUE;  
    }  
    else  
    {  
        return FALSE;  
    }  
} 

//对于DeleteFiber函数，如果给它传递一个无效的参数的话会抛出ERROR_INVALID_PARAMETER异常。如果进程正在被调试的话，异常会被调试器捕获。所以，同样可以通过验证LastError值来检测调试器的存在。如代码所示，0x57就是指ERROR_INVALID_PARAMETER。
BOOL CheckDebug()  
{  
    char fib[1024] = {0};  
    DeleteFiber(fib);  
    return (GetLastError() != 0x57);  
}

ZwSetInformationThread(GetCurrentThread(), ThreadHideFromDebugger, NULL, 0);

还有一个函数DebugActiveProcessStop与它的区别在于前者用于停止对指定进程的调试。

解决方案：在恶意代码运行期间修改恶意代码，使其不能调用探测调试器的API函数；修改这些api函数的返回值，确保恶意代码执行合适的路径；使用rootkit技术hook这些函数。

BeingDebugged属性：这个标志标识进程是否正在被调试。

ProcessHeap属性：Reserved4数组中一个未公开的位置叫做ProcessHeap，它被设置为加载器为进程分配的第一个堆的位置，第一个堆头部有一个属性字段，它告诉内核这个堆是否在调试器中创建。

NTGlobalFlag属性：系统使用PEB结构偏移量0x68处的一个未公开位置，来决定如何创建堆结构，如果这个位置的值为0x70，我们就知道进程正运行在调试器中。

解决方法：在执行跳转指令前，手动修改零标志，强制执行跳转；手动设置BeingDebugged属性值为0。

查找调试器引用的注册表项

调试器主要在AeDebug注册表的位置，

当应用程序发生错误时，默认情况触发Windows自带的Dr.Watson调试器，如果键值被修改为OllyDbg，则恶意代码可能正在被调试。

BOOL CheckDebug()  
{  
    BOOL is_64;  
    IsWow64Process(GetCurrentProcess(), &is_64);  
    HKEY hkey = NULL;  
    char key[] = "Debugger";  
    char reg_dir_32bit[] = "SOFTWARE\\Microsoft\\Windows NT\\CurrentVersion\\AeDebug";  
    char reg_dir_64bit[] = "SOFTWARE\\Wow6432Node\\Microsoft\\WindowsNT\\CurrentVersion\\AeDebug";  
    DWORD ret = 0;  
    if (is_64)  
    {  
        ret = RegCreateKeyA(HKEY_LOCAL_MACHINE, reg_dir_64bit, &hkey);  
    }  
    else  
    {  
        ret = RegCreateKeyA(HKEY_LOCAL_MACHINE, reg_dir_32bit, &hkey);  
    }  
    if (ret != ERROR_SUCCESS)  
    {  
        return FALSE;  
    }  
    char tmp[256];  
    DWORD len = 256;  
    DWORD type;  
    ret = RegQueryValueExA(hkey, key, NULL, &type, (LPBYTE)tmp, &len);  
    if (strstr(tmp, "OllyIce")!=NULL || strstr(tmp, "OllyDBG")!=NULL || strstr(tmp, "WinDbg")!=NULL || strstr(tmp, "x64dbg")!=NULL || strstr(tmp, "Immunity")!=NULL)  
    {  
        return TRUE;  
    }  
    else  
    {  
        return FALSE;  
    }  
}

识别调试器的行为

  • 软件断点检查

调试器设置软件断点的基本机制是使用软件中断指令INT 3（0xCC）临时替换运行程序中的一条指令，所以可能通过在代码查找机器码0xCC来判断是否被调试。

//repne scasb指令用于在一段数据缓冲区中搜索一个字节。
BOOL CheckDebug()  
{  
    PIMAGE_DOS_HEADER pDosHeader;  
    PIMAGE_NT_HEADERS32 pNtHeaders;  
    PIMAGE_SECTION_HEADER pSectionHeader;  
    DWORD dwBaseImage = (DWORD)GetModuleHandle(NULL);   
    pDosHeader = (PIMAGE_DOS_HEADER)dwBaseImage;  
    pNtHeaders = (PIMAGE_NT_HEADERS32)((DWORD)pDosHeader + pDosHeader->e_lfanew);  
    pSectionHeader = (PIMAGE_SECTION_HEADER)((DWORD)pNtHeaders + sizeof(pNtHeaders->Signature) + sizeof(IMAGE_FILE_HEADER) +   
                     (WORD)pNtHeaders->FileHeader.SizeOfOptionalHeader);  
    DWORD dwAddr = pSectionHeader->VirtualAddress + dwBaseImage;   
    DWORD dwCodeSize = pSectionHeader->SizeOfRawData;      
    BOOL Found = FALSE;  
    __asm  
    {  
        cld               
        mov     edi,dwAddr  
        mov     ecx,dwCodeSize  
        mov     al,0CCH   
        repne   scasb  
        jnz     NotFound  
        mov Found,1  
NotFound:           
    }  
    return Found;  
}
  • 硬件断点检查

OD中通过F2设置软件断点，ALT+F2设置硬件断点。设置硬件断点的基本机制是有DR八个寄存器，前四个用来设置断点，DR4和DR5由系统用保留，DR6和DR7用于记录断点的相关属性。所以，可以通过探测寄存器的值来判断是否被调试。

BOOL CheckDebug()  
{  
    CONTEXT context;    
    HANDLE hThread = GetCurrentThread();    
    context.ContextFlags = CONTEXT_DEBUG_REGISTERS;    
    GetThreadContext(hThread, &context);    
    if (context.Dr0 != 0 || context.Dr1 != 0 || context.Dr2 != 0 || context.Dr3!=0)     
    {    
        return TRUE;    
    }    
    return FALSE;    
}
  • 执行代码校验和检查

调试过程中可能存在对栈堆的修改，其哈希值就会被显著改变。将运行时计算得到的哈希值与存储的原始哈希值进行比对。如果两个哈希值相等，则代码未被篡改；如果不相等，说明代码可能被恶意篡改了。

  • 时钟检测

调试过程中，进程的运行速度会降低。因此，记录一段操作前后的时间戳，通过比较这两个时间戳，可以判断程序是否被调试。

rdtsc指令返回至系统重新启动以来的时钟数，并且将其作为一个64位的值存入EDX和EAX中。

BOOL CheckDebug()  
{  
    DWORD time1, time2;  
    __asm  
    {  
        rdtsc  
        mov time1, eax  
        rdtsc  
        mov time2, eax  
    }  
    if (time2 - time1 < 0xff)  
    {  
        return FALSE;  
    }  
    else  
    {  
        return TRUE;  
    }  
}

//GetTickCount函数返回最近系统重启时间与当前时间的相差毫秒数(由于时钟计数器的大小原因，计数器每49.7天就被重置一次)。

  • 判断父进程是否是explorer.exe

一般双击运行的进程的父进程都是explorer.exe，但是如果进程被调试父进程则是调试器进程。也就是说如果父进程不是explorer.exe则可以认为程序正在被调试。

  • 判断是否具有SeDebugPrivilege权限

调试器作为父进程的时候会有SeDebugPrivilege权限，如果父进程为调试器，则被调试的进程也会继承SeDebugPrivilege的权限，所以可以通过查看进程的权限来判断是否被调试。

干扰调试器的功能

  • 使用TLS回调

TLS 回调函数会在每个线程创建或终止时自动执行.

在IDA Pro中按Ctrl+E快捷键看到二进制的入口点，该组合键的作用是显示应用程序所有的入口点，其中包括TLS回调。双击函数名可以浏览回调函数。

  • 插入中断

因为调试器使用INT 3来设置软件断点，所以一种反调试技术就是在合法代码段中插入0xCC(INT 3)欺骗调试器，使其认为这些0xCC机器码是自己设置的断点。

BOOL CheckDebug()  
{  
      __try  
      {  
            __asm int 3  
      }  
      __except(1)  
      {  
            return FALSE;  
      }  
      return TRUE;  
}

双字节操作码0xCD03也可以产生INT 3中断，这是恶意代码干扰WinDbg调试器的有效方法。

BOOL CheckDebug()  
{  
      __try  
      {  
            __asm  
            {  
                  __emit 0xCD  
                  __emit 0x03  
            }  
      }  
      __except(1)  
      {  
            return FALSE;  
      }  
      return TRUE;   
}

INT 2D原为内核模式中用来触发断点异常的指令，也可以在用户模式下触发异常。但程序调试运行时不会触发异常，只是忽略。程序调试运行时，执行INT 2D之后不会运行SEH，而是跳过NOP，把bDebugging标志设置为1，跳转到normal_code；程序正常运行时，执行INT 2D之后触发SEH，在异常处理器中设置EIP并把bDebugging标志设置为0。

BOOL CheckDebug()  
{  
    BOOL bDebugging = FALSE;  
    __asm {  
        // install SEH  
        push handler  
        push DWORD ptr fs:[0]  
        mov DWORD ptr fs:[0], esp        
        int 0x2d  
        nop  
        mov bDebugging, 1  
        jmp normal_code  
handler:  
        mov eax, dword ptr ss:[esp+0xc]  
        mov dword ptr ds:[eax+0xb8], offset normal_code  
        mov bDebugging, 0  
        xor eax, eax  
        retn  
normal_code:  
        //   remove SEH  
        pop dword ptr fs:[0]  
        add esp, 4  
    }  
    printf("Trap Flag (INT 2D)\n");  
    if( bDebugging )  return 1;  
    else              return 0;  
}

}
  • 利用异常

当程序运行时，如果遇到无法处理的情况，就会抛出异常，被调试器接收处理，调试器通常会暂停程序执行，进而处理接收的异常，如果程序异常处理机制没有接收到异常，就说明可能正在被调试。所以，有的恶意软件可以通过故意引发异常，来让调试器捕获并处理。

RaiseException函数产生的若干不同类型的异常可以被调试器捕获。

BOOL TestExceptionCode(DWORD dwCode)  
{  
      __try  
      {  
            RaiseException(dwCode, 0, 0, 0);  
      }  
      __except(1)  
      {  
           return FALSE;  
      }  
      return TRUE;  
}  
BOOL CheckDebug()  
{  
      return TestExceptionCode(DBG_RIPEXCEPTION);      
}

SetUnhandledExceptionFilter函数可以修改系统最后的异常处理器。

EFLAGS寄存器的第八个比特位是陷阱标志位。如果设置了，就会产生一个单步异常。

调试器的漏洞

  • PE头漏洞
  1. PE文件的头部IMAGE_OPTIONAL_HEADER的结构：DataDirectory数组的大小被设置为IMAGE_NUMBEROF_DIRECTORY_ENTRIES，它等于0x10。因为DataDirectory数组不足以容纳超过0x10个目录项，所以当NumberOfRvaAndSizes大于0x10时，Windows加载器将会忽略NumberOfRvaAndSizes。OllyDbg遵循了这个标准，并且无论NumberOfRvaAndSizes是什么值，OllyDbg都使用它。因此，设置NumberOfRvaAndSizes为一个超过0x10的值，会导致在程序退出前，OllyDbg对用户弹出一个窗口。如图所示，使用LordPE打开可执行文件，修改RVA数及大小并保存，再用OllyDbg打开，会提示错误Bad or unknown format of 32-bit executable file。
  2. 节头部IMAGE_SECTION_HEADER的结构：Windows加载器使用VirtualSize和SizeOfRawData中的最小值将节数据映射到内存。如果SizeOfRawData大于VirtualSize，则仅将VirtualSize大小的数据复制入内存，忽略其余数据。因为OllyDbg仅使用SizeOfRawData，所以设置SizeOfRawData为一个类似0x77777777的大数值时，会导致OllyDbg崩溃。
  • OutputDebugString漏洞

恶意代码常尝试利用OllyDbg1.1的格式化字符串漏洞，为OutputDebugString函数提供一个%s字符串的参数，让OllyDbg崩溃。因此，需要注意程序中可疑的OutputDebugString调用，例如OutputDebugString(“%s%s%s%s%s%s%s%s%s”)。如果执行了这个调用，OllyDbg将会崩溃。
